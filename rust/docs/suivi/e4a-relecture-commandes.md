## E4A-01 Un fichier modifie dans tests/ fait verifier le projet depuis tests/
- Gravite : haute
- Ou : rust/crates/runtime/src/harness.rs:164-168 (verify_commands_for, recherche du dossier le plus proche) et :238-240, :265-266 (python_verify)
- Scenario : projet range comme test_claw, sans manifeste a la racine : `backend/` (pyproject.toml ou requirements.txt qui nomme pytest, `app/main.py`, `tests/test_api.py` qui fait `from app.main import app`) et `frontend/`. Le modele ecrit ou corrige `backend/tests/test_api.py` (cas tres courant). En fin de tour, verify_commands_for remonte les dossiers du fichier et s'arrete au PREMIER qui a une verification : `backend/tests` lui-meme. (a) Sans `tests/conftest.py` : python_verify(backend/tests) ne voit aucune config pytest dans ce dossier mais has_test_files(root) est vrai (il contient les `test_*.py`), et Claw lance `cd backend/tests && python -m unittest discover -q`. unittest importe `test_api` avec `backend/tests` seul dans sys.path : `from app.main import app` echoue (ImportError, que `tests/__init__.py` existe ou non), et des tests ecrits pour pytest ne sont de toute facon pas des TestCase. La verification echoue, et verification_gate renvoie au modele "Automatic verification after your changes failed... Find the root cause and fix it", jusqu'a trois fois : le modele part corriger un import qui marche quand les tests sont lances depuis `backend/` (ajout de sys.path, conversion en unittest, retouche des tests). (b) Avec `tests/conftest.py` (cas de test_claw) : pytest_configured est vrai dans `backend/tests` meme, Claw lance `cd backend/tests && python -m pytest -q -x` ; sans `tests/__init__.py` ni reglage `pythonpath`, `backend` n'est pas dans sys.path et l'import echoue de meme. Dans test_claw, `tests/__init__.py` existe (session-1791665810709, message 76) : l'import passe, mais si le modele a aussi touche `backend/app/main.py`, les deux dossiers `backend` et `backend/tests` sont retenus et la suite tourne deux fois.
- Preuve : `.take_while(|dir| dir.starts_with(&root) && *dir != root).find(|dir| !detect_verify_commands(dir).is_empty())` prend l'ancetre le plus proche ; python_verify tient `conftest.py` ou des fichiers de test du dossier lui-meme pour un projet (`["pytest.ini", "conftest.py"].iter().any(|name| root.join(name).is_file())`, `if has_test_files(root)`). Le test a_project_split_in_subfolders_is_verified_where_the_files_changed cree justement `backend/tests/conftest.py` mais ne modifie que `backend/app/main.py`, d'ou l'angle mort.
- Remede : dans verify_commands_for, retenir pour chaque fichier l'ancetre le plus haut sous la racine qui porte une verification (parcourir les ancetres jusqu'a la racine et garder le dernier trouve), ou ne jamais retenir un dossier nomme tests, test, __tests__ ou spec quand son parent en porte une ; puis retirer de `folders` tout dossier contenu dans un autre deja retenu. Ajouter au test le cas d'un fichier modifie dans `backend/tests/` (attendu : `cd backend && ... -m pytest -q -x`, une seule fois).
- Etat : corrigé (lot 2, dfecc27) : `verify_commands_for` prend le dossier le plus proche qui porte une vérification hors d'un dossier de tests (`in_tests_dir`).

## E4A-02 `pipefail` + `| head` : des tests qui passent sont comptes en echec
- Gravite : moyenne (sous Windows il faut plus de quelques Kio de sortie au-dela de ce que garde `head` : la suite de 72 tests de test_claw n'y arrive pas avec `head -100`)
- Ou : rust/crates/runtime/src/bash.rs:89-95 et :118-124 (execute_bash), :574-596 (hides_exit_code)
- Scenario : la commande exacte de la session S3 citee par E2-14, `python -m pytest tests/ -v --tb=short 2>&1 | head -100`, sur une suite qui passe entierement mais ecrit plus que ce que `head` garde. hides_exit_code rend Some(true) (filtre `head`), la commande part avec `set -o pipefail`. `head` sort apres 100 lignes ; Python ne meurt pas de SIGPIPE (il l'ignore) : sous Linux la premiere ecriture qui suit leve BrokenPipeError et pytest sort en erreur (1 par console_main, ou 3 si l'erreur survient pendant la session) ; sous Windows (Git Bash, aucun SIGPIPE pour un programme natif) l'ecriture echoue des que ce qui reste a ecrire depasse le tampon du tube (quelques Kio, une centaine de lignes de pytest -v), et Python sort avec 1 (OSError Errno 22) ou 120 (vidage final rate). Avec pipefail ce code devient celui de la commande : `returnCodeInterpretation: "exit_code:1"`. Le traitement du code 141 ne s'applique pas (seul un programme tue par SIGPIPE rend 141 : `yes`, `find`, `grep` de MSYS, git). Avant le lot 1 la meme commande rendait 0 (le code de `head`). Effets dans conversation.rs : command_outcome rend passed faux, after_tool met check_failed et check_failing a vrai (:1184-1186), failure_streak monte, StallGuard compte un echec ; le modele voit 100 lignes PASSED et un code 1 (le message d'erreur de Python est parti dans le tube ferme) et cherche une panne qui n'existe pas ; s'il retouche ensuite un test, TestGuard accuse a tort "modifie apres un echec". Meme chose pour `cargo test 2>&1 | head -50` (le binaire de test Rust ignore SIGPIPE, panique sur l'ecriture : 101) et tout programme natif sous Windows.
- Preuve : essai dans Git Bash 5.2 (msys) de cette machine, Python 3.13, avec PYTHONUNBUFFERED=1 comme le pose prepare_command : 150 lignes de 37 octets derriere `head -100` -> PIPESTATUS "0 0" ; 250 lignes -> "120 0" ; 600 lignes -> "1 0" ; 105 lignes de 74 octets -> "1 0" ; `yes | head -2` -> "141 0". Le test a_filter_at_the_end_of_a_pipe_does_not_hide_a_failure n'essaie que `yes | head -3`.
- Remede : quand le premier maillon est une verification (is_check_command), ne pas laisser `head` couper le programme : reecrire le dernier maillon `head ...` en `{ head ...; cat >/dev/null; }` (le reste de la sortie est lu et jete, la verification finit et pipefail rend son vrai code). Pour les autres programmes (producteur sans fin comme `yes`), garder la regle du 141. A defaut, quand `head` figure dans le tube et que le code n'est pas 0, ne compter la commande ni reussie ni en echec et joindre `[Claw] This output was cut by "| head": the program could not finish writing, so its exit code says nothing about the result. Run it again without "| head" (Claw keeps the beginning and the end of a long output).` Ajouter au test un programme qui ignore SIGPIPE (par exemple `python -c` qui ecrit 20 000 lignes derriere `head -5`).
- Etat : corrigé (lot 2, dfecc27), repris dans le lot 2b : une vérification suivie de filtres est réécrite `| { filtres` puis `cat >/dev/null; }`, elle finit toujours et rend son vrai code.

## E4A-03 Windows : KillShell, le delai depasse et la fin de Claw laissent vivants les petits-enfants natifs (serveur de dev, tests)
- Gravite : haute
- Ou : rust/crates/runtime/src/bash_tasks.rs:137-150 (Running::kill), :447-469 (stop), :495-501 (kill_all) ; rust/crates/runtime/src/bash.rs:809-824 (kill_shell_group), :828-849 (kill_process_tree)
- Scenario 1 (cas ordinaire, shell encore vivant) : sous Windows, `cd frontend && npm run dev` part d'office en arriere-plan (bash_N). Les processus sont : bash.exe de Git (le lanceur, enfant de Claw), usr/bin/bash.exe (le shell MSYS), le bash du script `npm`, node.exe de npm, puis cmd.exe (script-shell de npm sous Windows) et node.exe de vite, petits-enfants natifs inconnus de MSYS. Le modele appelle KillShell bash_N : stop() lance d'abord kill_shell_group, qui tue le groupe MSYS, donc le shell et node.exe de npm ; le lanceur, dont l'enfant vient de mourir, se termine aussitot ; puis kill_process_tree lance `taskkill /PID <lanceur> /T /F`, qui repond "processus introuvable" : l'arbre Windows n'est plus parcouru. cmd.exe et node.exe de vite survivent, gardent le port 5173 et les tubes ; stop() pose pourtant `killed = true`, BashOutput rend "exited", "killed": true, et le modele croit le serveur arrete (relance suivante sur 5174, ou "address already in use" pour un serveur Python lance par `uvicorn --reload`, dont le vrai serveur est aussi un petit-enfant). Meme ordre, meme effet dans Running::kill (delai fixe par le modele depasse, interruption de l'utilisateur : des tests `npm test` ou une compilation continuent apres "elle a ete arretee") et dans kill_all a la fin de Claw.
- Scenario 2 (processus laisse par `&`, shell deja fini) : `cd backend && python -m uvicorn app.main:app --reload --port 8000 &` devient une tache par LEFTOVER_GRACE (bash.rs:225-231). Ici le shell est fini depuis longtemps : meme dans l'ordre inverse, `taskkill /T` sur le lanceur ne trouverait rien ; le groupe MSYS n'atteint que le reloader, pas le serveur qu'il a lance.
- Preuve : trois essais sur cette machine, bash.exe de Git lance depuis un parent natif comme le fait Claw, un script Python parent qui lance un sous-processus Python (role de node.exe de npm et de vite). (a) Shell au premier plan vivant, ordre de Claw : `kill -KILL -- -67899; kill -KILL 67899` puis `taskkill /PID 32312 /T /F` -> "le processus 32312 est introuvable", le sous-processus 12544 tourne toujours. (b) Meme montage, ordre inverse : `taskkill /PID 10244 /T /F` d'abord arrete les six processus (lanceur, conhost, bash, parent et sous-processus), puis le groupe : aucun survivant. (c) Shell deja fini (`python parent.py > out.txt 2>&1 &`) : le groupe tue le parent, taskkill ne trouve pas le lanceur, le sous-processus survit. Les survivants ont ete arretes a la main par leur PID. Le script `npm` de Node sous Git Bash lance `"$NODE_EXE" "$NPM_CLI_JS" "$@"` et npm n'a pas de script-shell regle (cmd.exe par defaut). Les tests kills_long_running_tasks et a_process_left_running_with_an_ampersand_continues_in_the_background n'utilisent que `sleep`, un programme MSYS que le groupe atteint. Observation a part : `ps` montre encore sur cette machine un `python -m uvicorn app.main:app --host 0.0.0.0 --port 8000 ... &` (PID MSYS 52769, WINPID 29768) sous un sous-shell dont le parent a disparu, vivant depuis 23:38 la veille ; voie exacte non etablie, processus laisse intact.
- Remede : (1) dans Running::kill et stop, inverser l'ordre : kill_process_tree (`taskkill /T /F` sur le lanceur) d'abord, tant que l'arbre Windows est intact, puis kill_shell_group pour ce qui a quitte l'arbre (processus laisses par `&`). (2) Pour le scenario 2, dans kill_shell_group, avant le `kill -KILL` du groupe, lire avec `ps` de MSYS les WINPID des processus dont la colonne PGID vaut le PID du shell et lancer `taskkill /PID <winpid> /T /F` pour chacun. Plus solide pour les deux : placer le lanceur dans un Job Object a sa creation (bash_tasks::launch, CreateJobObjectW, AssignProcessToJobObject, JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE) et arreter par TerminateJobObject, qui atteint tous les descendants quelle que soit leur parente. Ne poser `killed = true` qu'apres avoir constate la fermeture des tubes. Ajouter un test Windows avec un sous-processus natif (`python -c` qui lance un autre `python -c`).
- Etat : corrigé (lot 2b, seconde partie) : `kill_command` arrête l'arbre Windows (`taskkill /T`) avant le groupe MSYS, et `kill_shell_group` arrête l'arbre de chaque processus Windows du groupe (lu dans `ps`) ; test Windows avec un petit-enfant Python, en arrière-plan et laissé par `&`. Pas d'objet de tâche Windows (Job Object) : il demanderait du code `unsafe`, interdit dans le projet.

## E4A-04 La verification imposee est sautee apres `npx tsc --noEmit || echo ...` en echec
- Gravite : moyenne (effet grave, travail livre casse sans verification ; forme de commande non observee dans les sessions de test_claw)
- Ou : rust/crates/runtime/src/harness.rs:321-337 (covers) ; rust/crates/runtime/src/conversation.rs:1177-1182 (after_tool) et :1312-1319 (verification_gate)
- Scenario : projet TypeScript (package.json sans script typecheck, tsconfig.json, tsc installe) : la verification du projet est `npx tsc --noEmit`. Le modele modifie `src/App.tsx` puis lance `npx tsc --noEmit && echo "OK" || echo "Erreurs de type"` (forme qu'ecrivent des modeles pour voir un message dans tous les cas, comme `; echo "exit=$?"`, `|| true` ou `2>&1 | wc -l` ; les trois sessions de test_claw n'en montrent pas, leur modele finissait par `| tail`). tsc trouve des erreurs et sort avec 2, le `|| echo` rend 0 : returnCodeInterpretation vide, pipefail n'y change rien (le dernier tube est `echo` seul, hides_exit_code rend None). after_tool range la commande dans verified_commands et remet check_failing a faux (la commande est une verification). Le modele conclut ; verification_gate appelle covers(commande du modele, "npx tsc --noEmit") : `ran.contains(&wanted)` est vrai, la verification est sautee, verify_failing passe a faux, le tour se termine avec des erreurs de type, sans la notice "Verification automatique" que l'utilisateur aurait vue. Meme chose pour `go build ./... && echo ok || echo ko`, et pour `cd frontend && npx tsc --noEmit || true` face a `cd frontend && npx tsc --noEmit`.
- Preuve : covers ne regarde que le texte (`if ran.contains(&wanted) { return true; }`), et verified_commands recoit toute commande dont le code de sortie est 0 (`if outcome.passed { ... aids.verified_commands.push(outcome.command); }`), sans regarder ce qui suit la verification dans la ligne. Aucun test ne couvre un `||` ou un `;` apres la verification.
- Remede : ne compter une commande du modele comme verification faite (covers, et la remise a faux de check_failing) que si son code de sortie est celui de la verification : distinguer dans shell_pieces `&&` (nouvelle variante Closed::And) de `||` et `;` (Closed::Or, Closed::Sequence) ; refuser la couverture si un morceau qui suit celui de la verification y est relie par `||`, `;`, une fin de ligne ou `&`, ou si le tube de la verification finit par un programme que hides_exit_code ne traite pas (`wc`, etc.). Ajouter ces cas au test a_project_split_in_subfolders_is_verified_where_the_files_changed (attendu : non couvert).
- Etat : corrigé (lot 2b) : `covers` et la remise à zéro de `check_failing` exigent que rien après la vérification ne masque son code (`exit_decided_at`, `exit_reflects_check`).

## E4A-05 Un serveur lance avec `&` et sa sortie dans un fichier n'est suivi par rien et survit a Claw
- Gravite : moyenne
- Ou : rust/crates/runtime/src/bash.rs:217-229 (run_in_foreground) ; rust/crates/runtime/src/bash_tasks.rs:153-160 (Running::finish) ; rust/crates/claw-cli/src/main.rs:119-122 (kill_all a la sortie)
- Scenario : le modele lance `cd backend && nohup python -m uvicorn app.main:app --port 8000 > server.log 2>&1 &` (forme que le test servers_and_watchers_are_recognized_but_builds_are_not cite lui-meme avec `nohup npm run dev > dev.log 2>&1 &`). starts_long_running rend faux, la commande part au premier plan, le shell finit aussitot. Comme la sortie du serveur va dans server.log, plus rien ne tient les tubes : run_in_foreground voit `open_pipes() == 0`, appelle finish() qui efface le fichier du PID du groupe, et rend un resultat termine, sans backgroundTaskId ni remarque. Le serveur tourne mais n'est connu d'aucune tache : le modele n'a aucun identifiant pour KillShell, `/bashes` ne le montre pas, et kill_all a la fin de Claw ne l'arrete pas, contrairement a ce qu'annonce main.rs ("Les serveurs de dev et autres commandes de fond ne survivent pas a Claw"). A la session suivante, `uvicorn ... --port 8000` echoue ("address already in use", Errno 10048 sous Windows) ou le modele interroge l'ancien serveur avec l'ancien code ; pour s'en sortir, un modele tente souvent `taskkill /F /IM python.exe`, qui tue tous les Python de l'utilisateur.
- Preuve : essai sur cette machine, bash.exe de Git lance depuis un parent natif avec stdout et stderr en tubes comme bash_tasks::launch, script de trois lignes `echo avant`, `python parent.py > server.log 2>&1 &`, `echo apres` : le shell finit et la fin de stdout arrive aussitot (tubes fermes), alors que parent.py et son sous-processus tournent toujours (arretes ensuite par leurs PID). Dans le code, la seule voie qui garde une trace d'un processus laisse par `&` est `running.open_pipes() > 0` (bash.rs:222-231).
- Remede : avant finish(), quand le shell est fini, regarder si son groupe a encore des membres : sous Windows, `ps` de MSYS, lignes dont la colonne PGID vaut le PID lu dans le fichier du groupe ; sous Unix, `kill -0 -<pid du shell>` (le shell est chef de groupe par process_group(0)). S'il en reste, garder le fichier du PID, enregistrer une tache (sortie vide) et joindre `[Claw] The command finished, but a process it started with & is still running in the background as bash_N (its output goes elsewhere). Stop it with KillShell when you are done.` ; kill_all l'arretera alors a la fin de Claw (avec le correctif de E4A-03 pour les petits-enfants natifs).
- Etat : a verifier

## E4A-06 hides_exit_code ne regarde que le dernier tube, alors que pipefail vaut pour tout le script
- Gravite : moyenne
- Ou : rust/crates/runtime/src/bash.rs:574-596 (hides_exit_code, `take_while` sur le seul dernier tube) et :89-95, :118-124 (execute_bash)
- Scenario 1 (echec compte reussi, comme E2-14) : `cd frontend && npm run build 2>&1 | tail -20 && echo "Build OK"`. shell_pieces donne `cd frontend` (sequence), `npm run build 2>&1` (tube), `tail -20` (sequence), `echo _`. Le dernier tube est `echo _` seul : la recherche de `start` ne trouve aucun maillon ferme par `|` juste avant lui, `.last()?` rend None, pas de pipefail. La compilation echoue, `tail` rend 0, le `&&` lance `echo "Build OK"`, la commande rend 0 : comptee reussie, check_failing remis a faux, rangee dans verified_commands, et la sortie montre "Failed to compile" suivi de "Build OK". Meme chose pour `npm run build 2>&1 | tail -30; echo "Exit code: $?"`, ou `$?` affiche meme le 0 de tail.
- Scenario 2 (le pipefail d'un tube change le sens des precedents) : `git log --oneline | head -5 && npm run build 2>&1 | head -40` dans un depot de plus de quelques centaines de commits. Le dernier tube declenche pipefail pour tout le script. git, coupe par `head -5`, sort avec 141 (SIGPIPE sous Linux, check_pipe de Git for Windows sous Windows) ; avec pipefail le premier tube vaut 141, le `&&` ne lance jamais la compilation, le script rend 141, et comme le dernier tube contient `head`, execute_bash efface ce 141 : commande reussie, verification (npm run build) comptee faite alors qu'elle n'a pas tourne.
- Preuve : `let start = (0..end.saturating_sub(1)).rev().take_while(|index| pieces[*index].1 == Closed::Pipe).last()?;` ne considere que les maillons qui precedent immediatement le dernier ; le prefixe PIPEFAIL est pose en tete du script entier (`format!("{PIPEFAIL}{}", input.command)`), et l'effacement du 141 (bash.rs:120-124) ne sait pas de quel tube vient ce code. Les tests ne couvrent ni un filtre suivi de `&&`/`;`, ni deux tubes.
- Remede : examiner chaque tube de la commande (shell_pieces decoupe deja les maillons ; les regrouper en tubes successifs) et ne proteger que les tubes concernes : faire rendre a shell_pieces la position de chaque maillon dans le texte, puis reecrire chaque tube concerne en sous-shell `(set -o pipefail; npm run build 2>&1 | tail -20)`, au lieu de poser pipefail en tete du script. Les autres tubes (`git log | head -5`) gardent leur sens, et l'effacement du 141 se decide tube par tube (dans le sous-shell : `(set -o pipefail; prog | head -40; s=$?; [ $s -eq 141 ] && s=0; exit $s)`), ce qui le retire de execute_bash.
- Etat : corrigé (lot 2b) : `with_faithful_exit_codes` réécrit chaque tube concerné dans son propre sous-shell `pipefail`, sous-shell producteur et substitutions compris.

## E4A-07 Avec un `timeout`, un serveur non reconnu bloque le tour jusqu'au bout du delai puis est tue
- Gravite : moyenne
- Ou : rust/crates/runtime/src/bash.rs:243-255 (run_in_foreground : `if explicit_timeout.is_none() && running.ready_and_idle(...)`), :116 (execute_bash), :147 (run_tool_command, meme regle pour PowerShell)
- Scenario : projet FastAPI dont `backend/main.py` finit par `uvicorn.run(app, port=8000)` (forme tres courante des projets ecrits par un modele ; de meme `node server.js`, `go run .`, `flask --app app run`, `php -S localhost:8000`, absents de LONG_RUNNING). Le modele appelle bash avec `{"command": "cd backend && python main.py", "timeout": 120000}`. starts_long_running rend faux, la commande part au premier plan ; uvicorn ecrit "Uvicorn running on http://0.0.0.0:8000 (Press CTRL+C to quit)", ready_at est pose. Mais parce que le modele a fixe un delai, la regle "serveur annonce pret puis silencieux 8 s : en arriere-plan" n'est jamais essayee : Claw attend les 120 s entieres, puis tue le serveur (timed_out_output). Le tour est bloque deux minutes (trois avec 180000, dix avec 600000) pour un serveur pret au bout de deux secondes, et le serveur que le modele voulait utiliser est mort ; il faut une requete de plus pour le relancer. Ce n'est pas un cas rare : dans session-1791665810709, le modele fixe `timeout` (30000 a 180000) sur 19 appels bash, y compris le lancement de son serveur.
- Preuve : bash.rs:243-255, la branche du delai depasse (`if explicit_timeout.is_some() { running.kill(); ... timed_out_output }`) passe avant, et la remise en arriere-plan d'un serveur pret est conditionnee a `explicit_timeout.is_none()`. Le test a_command_still_running_after_the_patience_continues_in_the_background n'essaie le serveur pret que sans delai.
- Remede : appliquer aussi ready_and_idle quand un delai est fixe, des que ce delai depasse ready_idle de beaucoup (par exemple au-dela de 20 s) : passer la commande en arriere-plan avec handed_off_output, dont la remarque dit deja comment lire la suite et l'arreter ; ne garder l'arret au delai que pour un delai court, qui dit qu'on voulait un essai borne.
- Etat : corrigé (lot 2b, seconde partie) : un serveur prêt et silencieux passe en arrière-plan dès que le délai fixé atteint 20 s (`READY_HANDOFF_MIN_TIMEOUT_MS`).

## E4A-08 Du code modifie par une commande (sed, heredoc, script Python) n'est jamais verifie
- Gravite : moyenne
- Ou : rust/crates/runtime/src/conversation.rs:1140-1147 (after_tool : seuls edit_file, write_file et NotebookEdit posent `dirty`) et :1295-1302 (verification_gate : `|| !aids.dirty` sort aussitot)
- Scenario : le modele echoue deux fois a modifier `frontend/src/app/page.tsx` avec edit_file ("text not found", cas frequent chez les modeles gratuits, que StallGuard signale lui-meme) et passe par une commande : `sed -i 's/const items = data/const items: Item[] = data/' frontend/src/app/page.tsx`, ou `python - <<'EOF'` qui lit, remplace et reecrit le fichier, ou `cat > backend/app/routes.py <<'EOF' ... EOF`. La commande reussit. after_tool ne pose `dirty` que pour edit_file, write_file et NotebookEdit : le tour n'est pas marque modifie, `originals` ne connait pas le fichier. Le modele conclut ; verification_gate sort sur `!aids.dirty` avant meme de chercher une verification : ni `cd frontend && npx tsc --noEmit`, ni la notice "Verification automatique", ni l'avertissement "aucune verification connue". Si la modification casse la compilation, le tour se termine sans que Claw le voie, alors que l'utilisateur croit que Claw verifie apres chaque modification. Le cas se produit justement quand le modele a deja du mal a modifier le fichier.
- Preuve : `dirty` n'est pose qu'en deux endroits, conversation.rs:1141 (outils d'edition) et :1367 (verification en echec) ; StallGuard reconnait pourtant qu'une commande "a pu changer l'etat du projet" (harness.rs:771-779, il efface passed_checks pour toute commande qui n'est pas une verification). Aucun test ne fait modifier un fichier par bash avant la fin d'un tour.
- Remede : prendre au debut du tour une empreinte de l'etat des fichiers du projet (`git status --porcelain -uall` quand le dossier est un depot, sinon tailles et dates de modification des fichiers hors dossiers generes, comme le fait deja file_ops::generated_dir) ; dans verification_gate, si `dirty` est faux, la comparer a l'etat courant et, si elle a change, poser `dirty` et ajouter les fichiers changes a la liste `changed` passee a verify_commands_for. Pas de cout par commande, et les modifications faites par bash ou PowerShell sont verifiees comme les autres.
